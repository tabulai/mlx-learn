# KNN: packed loads, scalar selection and input-buffer reuse

This pass adds three optimizations to the preceding KNN implementation. It also
separates intermittent-use latency from fully warmed measurements after finding
a repeatable idle-to-active performance ramp. The existing short-warmup reports
remain unchanged; their measurements are not replaced by the faster warmed ones.

On 50,000 × 32 data, fully warmed neighbor queries now take **0.704–0.739 ms**,
**4–6% faster than the immediately preceding implementation**. Float64-input
fit-plus-query improves **1.443 → 1.021 ms**. Fully warmed queries exceed 2×
default-thread sklearn, but intermittent calls remain below that target and one
warmed indices-only block also misses it. The full operation tables preserve
those limitations.

The immediately preceding implementation is frozen in
[`knn-pre-v2-2026-10-28.zip`](../benchmarks/reference/knn-pre-v2-2026-10-28.zip).
Its 53 source hashes match the previous final benchmark. The new implementation
has 54 source files, including the new Metal source generator.

## Implemented changes

1. **Packed feature loads.** Two-query scans load four adjacent features with
   `packed_float4` when the feature count is divisible by four. The compensated
   updates still run in their original x/y/z/w order. Packed storage works with
   float-offset input views; it does not impose a new 16-byte alignment
   requirement. Other feature widths retain scalar loads.
2. **Scalar top-k state for k=5.** Named candidate scalars replace dynamically
   indexed private arrays for the default neighbor count. Insertion expands the
   four possible shifts, and a winning lane shifts its sorted list after each
   SIMD reduction. Other k values retain the general selector. Four cached source
   variants cover the two selection methods and two loading methods; model data
   and completed query results are never cached globally.
3. **Reuse the owned float64 conversion buffer.** A successful checked cast already
   allocates private contiguous float32 storage. When sklearn validation returns
   that same buffer, the index takes ownership instead of copying it again.
   Float32 inputs, subclasses and other containers retain their existing copy
   behavior. User input and device storage remain isolated, including after
   mutation, refitting and pickling.

The NumPy-free native API remains independent of sklearn and NumPy. The input
reuse change belongs to the sklearn compatibility layer. The new kernels scan
all references and preserve the existing compensated arithmetic, tie ordering,
self-exclusion and overflow behavior. Measured outputs match the preceding
implementation bit for bit.

## What the profiling established

An A/A control used identical source hashes for both worker implementations.
Reference/current median ratios ranged from 0.986 to 1.100, with median 1.014;
most differed by less than 4%. This did not establish a large process bias.
Adding idle GPU workers also failed to reproduce a substantial slowdown by
itself.

A **one-second idle period** did reproduce the slowdown in a single unchanged
worker. Across 200 consecutive audited queries, successive 20-call medians were
approximately 3.07, 3.11, 2.99, 2.90, 1.71, 1.50, 1.02, 0.89, 0.81 and 0.77 ms.
The next 200 calls stayed near 0.75–0.78 ms. Another one-second idle period
reintroduced the ramp. This demonstrates an idle/warm-state effect; GPU clock
frequency was not measured, so a specific power-management cause is not claimed.

Three or five warmups therefore did not establish sustained performance on this
machine. In particular, the earlier report's 25-call “sustained-use” protocol
could remain inside the ramp. Its timings remain valid for that protocol, but
should not be described as fully warmed GPU measurements.

Evidence: [A/A control](../benchmarks/results/knn-v2-aa-control-2026-10-28.json),
[phase profile](../benchmarks/results/knn-latency-profile-v2-2026-10-28.json),
and [idle/ramp experiment](../benchmarks/results/knn-idle-ramp-probe-2026-10-28.json).

## Benchmark definitions

The main workload has **50,000 training rows, 32 features, 256 query rows and k=5**.
It is not a 50,000-row self-query. Three datasets use seeds 51, 52 and 53, with
two copied training rows in each query batch to exercise zero-distance weighting.
Hardware is an Apple M4 Max with 128 GiB memory; MLX 0.32.2, sklearn 1.9.0 and
NumPy 2.5.2. Default sklearn retains its sixteen OpenMP threads.

Both protocols include public validation, NumPy input/output boundaries and all
GPU work. Fresh fit-plus-query constructs a new model for every sample. Accuracy
audits run outside each timer and require exact neighbor indices, distance
`atol=rtol=1e-6`, and matching classifier/regressor outputs. Backend and source
hash checks guard every run.

- **Interleaved, short warmup:** the original alternating-worker protocol, three
  warmups and nine measured calls per operation. This preserves comparability
  with earlier reports and exposes intermittent-use behavior.
- **Fully warmed:** each operation and variant gets at least one second of
  continuous audited calls, followed by 25 timed calls in that worker. The same
  policy applies to current, frozen, single-thread sklearn and default-thread
  sklearn. Actual warmup count and duration are recorded and checked. No power,
  priority, thread-count or OpenMP wait-policy settings are changed.

The strict aggregate gate requires all nine search/inference/fresh-fit operation
medians to exceed 2× default sklearn on all three datasets; fit alone is separate.
The warmed run passes **26 of 27** combinations, so that strict gate remains
false. Its one miss is indices-only search for seed 52: 2.438 ms versus sklearn's
4.573 ms (1.88×). Distance-weighted classification on that seed also slowed
relative to the frozen version, although it remained above 2× sklearn. Neither
measurement is discarded.

A separate, predeclared three-block diagnostic on the same seed did not reproduce
an indices-only regression: paired medians for distance/indices calls were
0.947/0.909, 0.741/0.708 and 0.697/0.680 ms. That observation does not replace the
original failed block or establish its cause.

The fully warmed neighbor-query medians improve **1.04–1.06×** over the preceding
version and measure **6.21–8.13×** default sklearn. Fresh fit-plus-query measures
**3.91–4.18×** default sklearn, with little change versus the preceding version.
Most of the difference from earlier absolute timings is the warm-state effect,
not the incremental code changes. With the original short warmup, queries improve
**1.05–1.10×** over the preceding version but remain only **1.59–1.81×** default
sklearn. An unconditional 2× latency claim is not supported.

## Float64 input and temporary memory

A separate input-conversion benchmark widens the same float32 fixture exactly to
float64. MLX's established policy converts it back to float32; sklearn processes
the float64 input. This isolates the conversion-buffer optimization without
changing the represented data values, and does not replace the float32 target.

Fit improves from **0.534 to 0.385 ms** (1.39×), and fresh fit-plus-query improves
from **1.443 to 1.021 ms** (1.41×). All ten operations pass the accuracy audit.

Separate five-fit `tracemalloc` measurements show median traced peak allocation
falling from **12,804,258 to 8,002,601 bytes**, a **37.5% reduction**. Retained host
allocation remains 6,402,554 bytes. One 6.4 MB copy is eliminated, while peak
allocation drops by 4.8 MB because the finiteness-check temporary overlaps
differently. These are traced Python/NumPy allocations, not total process RSS,
Metal memory or total unified-memory use.

## Other ideas tested

Cooperative shared training tiles were correct but slower: the best larger-query
group measured about 0.893 ms versus 0.731 ms for the existing paired kernel.
Partition-major and bundled-query scheduling gave no public-call improvement.
These designs were not enabled in production. Packed loads and scalar candidates
showed modest, repeatable gains and retained the accuracy contracts.
